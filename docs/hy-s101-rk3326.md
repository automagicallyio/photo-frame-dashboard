# HY-S101 Frameo frame (brand `zyf`, Rockchip RK3326, Android 8.1)

One unit, set up on 2026-10-22 from an Apple silicon Mac. This is a record of what was done on that unit, not a tested procedure for other units. It has the same logical NAND layout as the [Akimart ZN-DP1002](akimart-zn-dp1002.md), but a different firmware, and `adb root` does not work. Compare the build strings in the first table before you reuse anything from this page.

Follow the [repository's approval and privacy rules](../README.md#rules-we-learned-the-hard-way). The goal on this unit was a plain Android frame with no vendor apps, running a web dashboard in WebView.

## Cables and ADB

- Frameo Settings → About → Beta Program → ADB Access turned on USB ADB. The authorization prompt appeared on the frame and was accepted. The device showed as `2207:0006`.
- **USB-C to USB-C from the Mac: no data.**
- **A USB-C to USB-A adapter on the Mac plus a USB-A to USB-C cable: works.** This answers the open question in [frameo-rk3326-s101.md](frameo-rk3326-s101.md#open-questions) for this board.

## Root is `su <uid>` with two capabilities

- `/system/xbin/su` is `-rwsr-sr-x root shell`. `su 0 <cmd>` runs as uid 0. `su -c` fails with `su: invalid uid/gid '-c'`.
- The root shell keeps the `u:r:shell:s0` context and has only `CAP_SETUID` and `CAP_SETGID` (`CapEff` `00000000000000c0`). It has no `CAP_DAC_OVERRIDE` and no `CAP_SYS_ADMIN`.
- Effects of the missing capabilities:
  - Root cannot read files owned by other users. Switch to the owner instead, for example `su 1000` for `system` files and the `frp` partition, and `su 1023` for `media_rw`.
  - `/system` cannot be remounted read-write, and zram cannot be resized (360 MB `zram0` stays as shipped).
  - Block devices that root owns can be read and written with `su 0 dd`.
- This build's `dd` prints `dd: conv option disabled` for any `conv=` option. The shell has no `awk`. `sha256sum` and `gzip` are present.

## Verified firmware backup

Captured like the [Akimart backup](akimart-zn-dp1002.md#verified-firmware-backup): `adb exec-out "su <owner uid> dd ..."` for the first 8 MiB of `rknand0` and then each partition p1 to p15 in chunks. `adb exec-out` carried binary data unchanged.

- Result: 3,414,687,744 bytes (sectors 0 to 6,669,311, everything before userdata). The gzip readback matched, no aligned 4 KiB block was all `0xCC`, and the on-device SHA-256 of all 16 regions matched.
- `frp` (p15) is owned by `system`, so it was read with `su 1000`.
- Restore is untested. No userdata backup was taken. `/data` held only the Frameo setup then.

Before removing packages in bulk, copy `/data/system/users/0/package-restrictions.xml` with `su 1000 cp`. If Android does not boot, copying it back and rebooting should undo every `pm uninstall --user 0` at once (not tested).

### Wait before you reboot after `pm uninstall --user 0`

Android writes the change to `/data/system/users/0/package-restrictions.xml` about 10 s after the command. On this unit, a reboot inside that window brought Frameo back. Before you reboot, make sure that the file has the entry:

```sh
adb shell "su 1000 grep 'name=\"net.frameo.frame\"[^>]*inst=\"false\"' /data/system/users/0/package-restrictions.xml"
```

### The boot screens are black

The frame shows two images while it starts: the boot logo from the bootloader and kernel, then Android's boot animation. Both showed a Frameo logo.

**Boot animation.** Rockchip's `libbootanimation.so` plays `/data/local/bootanimation.ts` instead of `/system/media/bootanimation.zip` when `persist.sys.bootvideo.enable` is 1. This needs no `/system` write. The file used here was a 1 s black H.264 MPEG-TS video, 1280×800, 25 fps, 12,220 bytes (SHA-256 `de8353d8a6d9a2025ac5b627ae03f9e7dcc319cb1af2a3c5d440b2da7fe0c262`).

The video is at `/data/local/bootanimation.ts`, owned by root, mode 0644, and `su 0 setprop persist.sys.bootvideo.enable 1` turns it on.

Undo: `su 0 setprop persist.sys.bootvideo.enable 0` and `su 0 rm /data/local/bootanimation.ts`.

**Boot logo.** This is a write to flash, recorded here as a one-unit result. The repo has no guarded script for it.

- `logo.bmp` and `logo_kernel.bmp` are in the `resource` partition (rknand0p4, 16 MiB), a Rockchip `RSCE` image. Both are 800×1280 8-bit BMPs of 1,025,076 bytes, stored back to back in partition sectors 213 to 4,218.
- Stock partition SHA-256 on this firmware: `9e1f2ebf2b193d999b7ce3a3d88a1e8c1aa2c4c0239c07f72a4b3a8f7de9ead7`. The live partition had this hash before the write.
- Both BMPs were replaced with black BMPs of the same size and header. No other byte changed, including the device tree. The patched partition hashes to `8c6fe52c46baad89377e0ec45a567eee697a12d72f6640ef9674e62c53093725`.
- Only the 4,006 changed sectors were written, with `su 0 dd ... bs=512 seek=213 count=4006` from a segment pushed to the frame (the report doesn't say whether its SHA-256 was checked on the frame before the write). The partition read back with the patched hash, and the same hash again after a reboot.
- Undo: write sectors 213 to 4,218 of the stock partition from the backup back the same way.
